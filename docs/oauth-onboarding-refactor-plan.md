# 카카오 로그인 및 프론트엔드 온보딩 전환 구현 계획서

작성일: 2026-09-15 · 대상: 현재 develop 작업 트리 · 상태: 구현 및 서버 검증 완료

## 1. 목표와 범위

카카오 OAuth로 먼저 로그인한 뒤 프론트엔드 온보딩에서 프로필·보호자 연락처를 입력하고 서비스 동의를 받는다. 화면 단계와 안내 확인 여부는 서버에 저장하지 않는다. 프론트엔드가 임시 캐시로 화면 전환을 관리하며, 새 로그인이나 캐시 만료 후에는 첫 온보딩 화면부터 시작한다.

서버는 인증, 실제 사용자 데이터, 동의 이력, 기능 실행에 필요한 조건만 관리한다. 기존에 확정한 정책대로 서비스 문서는 프론트엔드 정적 콘텐츠이며 동의 문서 버전은 1이다. 프로필·연락처의 낙관적 잠금용 version은 이 문서 버전과 별개로 유지한다.

첨부 화면은 로그인 → 카카오 인증 → 기본 정보 → 보호자 연락처 → 서비스 동의 → 기기 권한 순서를 이해하는 자료로 사용했다. 화면 속 작은 문구를 별도의 요구사항으로 해석하지 않았다. 현재 작업 공간에는 프론트엔드 소스가 없어 서버 구현과 프론트 연동 명세가 구현 범위다.

이 계획은 사용자 승인 후 구현에 착수했다. 현재 연동 계약은 frontend-onboarding.md를 따른다.

## 2. 현재 구현에서 확인한 문제

| 위치 | 현재 동작 | 변경 이유 |
|---|---|---|
| A02 / OAuthTransactions | LOGIN에 동의 3개를 요구하고 oauthConsent에 저장 | 동의 화면이 로그인 이후에 있음 |
| OAuth 콜백 | 동의를 재검증하고 consentEvent 기록, 카카오 프로필 저장 | 인증과 서비스 동의 처리가 결합됨 |
| A06·A07 / AuthTransactions | webSession.onboardingStep 조회·진행, 단계별 검증 | 프론트 화면 상태가 서버에 종속됨 |
| AuthRepository.advance | COMPLETE에서 appUser를 ACTIVE로 변경 | API만 삭제하면 활성화 처리가 사라짐 |
| AccountLocalCleanup | ONBOARDING 계정을 생성 24시간 후 정리 | 활성화 경로를 없애면 정상 계정도 정리될 수 있음 |
| H01·C01·M01 | COMPLETE 또는 MESSAGE_TEST 단계 검사 | 온보딩 API 삭제 후 기능이 계속 차단될 수 있음 |
| U02·U08~U10 | 개인정보 동의가 먼저 저장돼 있어야 실행 가능 | U05와 동시 요청하면 도착 순서에 따라 실패 |

현재도 일반 카카오 로그인 성공 시에는 PROFILE로 초기화한다. 다만 같은 세션의 단계 복원, 기능 사용 제한, 계정 활성화가 서버 단계에 연결돼 있어 요청한 구조와 다르다.

## 3. 변경 후 로그인 계약

### A02: POST /api/v1/auth/kakao/authorization

요청에서 decisions를 제거한다.

```json
{ "purpose": "LOGIN" }
```

재인증은 기존대로 `{"purpose":"REAUTH"}`를 사용한다. 응답의 authorizationUrl·expiresAt은 유지한다. 동의 누락 때문에 A02가 422를 반환하는 경로를 없앤다. 구형 decisions 필드는 새 Swagger와 요청 DTO에서 제거하고, 알 수 없는 필드 처리 정책과 일관되게 검증한다.

### OAuth 콜백

1. state·세션 연결·만료·일회성 사용을 검증한다.
2. 카카오 인증 코드를 교환하고 계정을 식별한다.
3. 신규 계정에는 로그인 식별에 필요한 최소 계정 정보만 생성한다. 서비스 동의 이력은 생성하지 않는다.
4. 로그인 세션과 CSRF를 교체한다. 일반 로그인에서는 민감 작업 재인증 시각을 부여하지 않는다.
5. 기존 `/onboarding/profile` 진입 경로를 사용할 수 있으나, 이것은 최초 진입 주소일 뿐 서버의 단계 저장·복원 기능이 아니다. 프론트는 LOGIN 성공 시 이전 캐시를 초기화한다. REAUTH는 기존 설정 화면 복귀를 유지한다.

카카오에서 받은 이름·전화번호·성별·생년월일을 서비스 동의 전에 자동 저장하던 동작은 제거하는 안을 기본으로 한다. 신규 프로필은 빈 값으로 시작하고 U02에서 사용자 입력을 저장한다. 기존 계정의 프로필·동의는 로그인만으로 덮어쓰거나 자동 재동의하지 않는다.

현재 login-scopes 기본값이 이름·성별·생년월일·전화번호를 요청하므로 설정과 카카오 응답 매핑도 함께 정리한다. 카카오 정보 자동 채움까지 유지하려면 동의 전 임시 데이터의 전달·수명 계약이 별도로 필요하다. 이 계획의 기본 범위에는 포함하지 않는다.

카카오 자체 동의 화면, SafeCall 서비스 동의, 마이크·위치의 기기 권한은 서로 별개다. OAuth 요청에 SafeCall 동의나 기기 권한을 넣지 않는다.

## 5. 개인정보 화면의 한 번의 다음 클릭 처리

앞선 프로필·연락처 화면에서는 입력을 프론트 임시 상태에 보관한다. 개인정보 동의 화면의 다음 클릭을 한 번의 저장 동작으로 묶고, 모든 필수 저장이 성공한 뒤 다음 화면으로 이동한다.

**요청한 세 종류 API의 완전 동시 호출은 현재 동의 선행 조건과 충돌한다. 권장 구현은 같은 클릭 안에서 U05 → U02 → 연락처 변경 요청 순으로 실행하는 것이다.** 사용자에게 버튼을 여러 번 누르게 하지는 않는다.

순서가 필요한 이유:

- U02와 연락처 저장은 U05가 커밋한 동의를 검증한다. Promise.all로 동시에 시작하면 동의 저장보다 먼저 실행될 수 있다.
- 프로필 전화번호와 보호자 전화번호가 같으면 안 된다. U02 저장 후 연락처 요청을 실행하면 새 본인 번호를 기준으로 검증할 수 있다.
- 독립 API 3개는 하나의 DB 트랜잭션이 아니다. 일부 성공 후 실패하는 경우를 프론트에서 처리해야 한다.

프론트 처리 계약:

1. 클릭 시 입력 전체를 검증하고 중복 클릭을 막는다.
2. U05에 개인정보·AI 통화·위치 동의를 version 1로 전송한다. 필수 동의 미선택 시 다음으로 이동하지 않는다.
3. U02로 프로필을 저장한다.
4. 연락처별 신규/변경/삭제 여부에 따라 U08/U09/U10을 호출한다. 연락처가 2명이면 요청 수는 총 3회를 넘을 수 있다.
5. 모두 성공하면 임시 입력을 정리하고 권한 화면으로 이동한다.
6. 부분 실패 시 현재 화면과 성공 결과를 유지하고 실패한 요청만 재시도한다. 동일 요청 재시도에는 같은 Idempotency-Key를 사용한다. 입력을 바꿔 재전송하면 새 키를 쓴다.
7. 409 version 충돌은 해당 리소스를 재조회해 조정한다. 재로그인 시에도 저장된 연락처 ID를 조회하여 중복 등록하지 않는다.

기존 연락처 번호를 본인 번호로 바꾸는 등 교차 변경은 충돌 연락처를 먼저 수정·삭제하는 별도 순서를 적용한다. 모든 API의 실제 데이터 검증은 유지한다.

완전한 네트워크 동시 실행이 필수라면 이 부분은 구현 전 추가 설계가 필요하다. 별도 API 사이의 동의 선행 조건을 없애거나 새 임시 저장/일괄 커밋 구조를 도입해야 하므로, 단순히 Promise.all만 적용하는 방식은 계획에 포함하지 않는다.

## 6. 화면 캐시와 기기 권한

- 프론트 메모리 캐시를 기본으로 한다. 새 로그인·로그아웃·세션 만료·계정 전환 시 초기화하고 첫 온보딩 화면부터 표시한다.
- 같은 실행 중 화면 이동은 캐시로 처리한다. 장시간 방치 후 복원 여부는 프론트 TTL로만 결정하며, 정확한 TTL은 프론트 설정값으로 둔다. 서버 만료와 화면 캐시 만료를 동일 개념으로 취급하지 않는다.
- 새로고침 복원을 위해 sessionStorage를 선택할 경우에도 만료 시각을 두고 민감한 입력의 장기 보관을 피한다. 기본 메모리 방식에서는 새로고침 시 처음부터 시작한다.
- 기존 프로필·연락처·동의가 있다고 중간 화면으로 건너뛰지 않는다. 필요하면 해당 화면의 초기값으로 조회해 표시한다.
- 권한 안내·SOS 안내·테스트 건너뛰기에는 서버 API를 호출하지 않는다. 권한 요청과 현재 허용 여부 확인은 프론트에서 수행한다.
- 실제 통화·메시지 작성 때만 C01·M01 등 해당 기능 API를 호출한다. 클라이언트의 단계 캐시나 권한 플래그를 서버 접근 권한의 증거로 사용하지 않는다.

## 7. DB와 계정 수명 주기

1. oauthConsent 테이블과 모든 참조를 제거한다. oauthAttempt는 OAuth 보안 검증을 위해 유지한다. 기존 consentEvent는 보존한다.
2. webSession.onboardingStep과 관련 CHECK 3개를 제거한다. 온보딩 전용 version 및 CHECK도 참조 전수 확인 후 제거한다.
3. appUser의 ONBOARDING 상태를 제거하고 신규 계정은 ACTIVE로 만든다. ACTIVE는 로그인 가능한 계정이라는 의미로 한정하며, 서비스 이용 가능 여부는 실제 데이터로 검증한다.
4. 기존 ONBOARDING 계정은 ACTIVE로 이관한다. 필수 동의를 자동 생성하거나 프로필 확인 시각을 채우지 않는다. DELETION_PENDING은 유지한다.
5. AccountLocalCleanup의 '온보딩 24시간 미완료 계정 삭제' 분기를 제거한다. 명시적 탈퇴·동의 철회·기존 삭제 작업 처리 경로는 유지한다. 별도의 미동의 계정 보유 기간은 화면 상태와 분리된 정책으로 추후 다룬다.
6. LocalDeletionTransactions 등 ONBOARDING을 계정 상태로 취급하는 코드도 함께 수정한다.
7. 신규 설치 DDL과 design 물리·논리 설계에 반영하고 기존 DB용 마이그레이션을 별도로 작성한다. 앞서 작성된 정적 문서 전환 마이그레이션과 적용 순서를 명시한다.

구형 서버는 제거된 컬럼을 읽기 때문에 신·구 서버 혼용 배포를 하지 않는다. 서비스 중지 → 진행 중 OAuth 시도 만료 및 필요 세션 정리 → 마이그레이션 → 새 서버·프론트 적용 순서를 문서화한다. DDL의 암묵적 커밋을 고려해 백업 복구 절차를 함께 정리한다. 실제 DB 적용은 구현 검증과 별도 작업이다.

## 8. 구현 순서

1. AuthDtos·AuthController·OAuthTransactions·OAuthService를 수정하고 OAuth 동의 스냅샷 의존성을 제거한다.
2. A06·A07, Step·AdvanceRequest·OnboardingView, 관련 저장·응답 필드를 제거한다. 기기 Permission처럼 통화에서 쓰는 타입은 유지한다.
3. 계정 생성·정리·삭제 코드를 새 계정 상태 의미에 맞춘다.
4. U01 및 초기 프로필 조회 계약을 조정하고 U02·U05·연락처 API의 최초 저장, 재수정, 부분 실패 계약을 정리한다.
5. H01·C01·M01의 단계 검사를 실제 데이터 검사로 교체한다. 통화 생성과 연결에서 공유하는 검사까지 점검한다.
6. 신규/기존 DB 스크립트, Swagger, API 명세, 프론트 연동 문서, 운영·검증 문서를 함께 갱신한다.
7. 테스트 fixture의 온보딩 진행 호출을 제거하고 독립 리소스 준비 방식으로 전환한다.

## 9. 검증 및 완료 기준

- 동의 없는 신규 사용자도 A02 LOGIN을 시작하고 콜백으로 로그인할 수 있다. 콜백이 서비스 동의와 카카오 프로필을 자동 저장하지 않는다.
- state 재사용·만료·다른 세션·잘못된 계정 재인증·탈퇴 중 계정 접근 차단이 유지된다.
- A06·A07은 라우트와 OpenAPI에서 사라지고 A01·A05 응답에 onboardingStep이 없다.
- 신규 로그인 후 U01에서 빈 초기값과 version을 받으며 U05 → U02 → U08 저장이 성공한다.
- 동의 없는 직접 프로필/연락처 저장과 기능 실행은 정해진 오류로 차단된다. 개인정보·AI 동의는 독립적으로 검증한다.
- 프로필 재수정, 연락처 2명 등록·수정·삭제, 중복 번호, 부분 실패 후 재시도, Idempotency-Key 충돌, version 충돌을 검증한다.
- 온보딩 API 호출 없이 실제 조건을 충족한 회원이 통화·메시지 기능을 쓸 수 있다. 조건 미충족은 화면 단계 대신 구체적인 사유를 반환한다.
- 게스트 통화, 기존 회원 재로그인, 동의 철회, 정리 작업 중 재동의/데이터 저장 차단을 회귀 검증한다.
- 기존 ONBOARDING 계정 이관 후 자동 삭제되지 않고 기존 동의·프로필·연락처가 보존되는지 마이그레이션 테스트로 확인한다.
- 서버 단위·통합 테스트와 설계 검증을 수행한다. 프론트의 캐시 만료·재로그인 첫 화면·한 번 클릭 저장 UX는 프론트 저장소에서 별도 확인한다.

계획 검토 시 핵심 조정 사항은 두 가지다. 세 API는 한 클릭 안에서 순서대로 저장하는 안을 권장하며, 카카오 프로필 자동 채움은 기본안에서 제거한다. 이 두 사항을 포함한 계획을 기준으로 구현 범위를 확정한다.
