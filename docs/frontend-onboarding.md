# 로그인 이후 온보딩 연동

화면 단계·안내 확인·완료 여부는 프론트 메모리 캐시로 관리한다. 서버에는 단계 조회/진행 API가 없다. 로그인 성공, 로그아웃, 계정 전환, 세션 만료, 캐시 만료 시 캐시를 초기화하고 첫 온보딩 화면부터 표시한다. 재로그인 시 기존 데이터가 있어도 화면을 건너뛰지 않는다. 캐시 TTL은 프론트 설정이며 메모리 캐시는 새로고침 시 초기화된다.

## 로그인

1. A05 `GET /api/v1/auth/session`으로 쿠키·CSRF를 준비한다.
2. A02에 `{"purpose":"LOGIN"}`만 전송하고 authorizationUrl로 이동한다. decisions는 허용하지 않는다.
3. 서버 콜백은 계정을 식별하고 새 세션을 발급한 뒤 `/onboarding/profile`로 이동한다. 카카오 제공 프로필은 DB에 저장하지 않고 새 로그인 세션에 묶인 암호화된 HttpOnly 쿠키에 최대 10분간 보관한다.
4. A05를 다시 호출하여 교체된 CSRF와 `profilePrefill`을 받는다. A05는 값을 반환한 뒤 자동 채움 쿠키를 즉시 삭제하며 응답에는 onboardingStep이 없다.

프론트는 `profilePrefill`의 이름·성별·생년월일·전화번호를 입력 필드에 채우고, 제공되지 않은 값은 사용자가 직접 입력하게 한다. 이 값은 프론트 캐시에만 유지하고 U05 동의 저장 후 U02로 사용자가 확인한 값을 저장한다. 기기 권한과 SafeCall 동의는 카카오 로그인 이후 별도로 받는다. REAUTH는 `{"purpose":"REAUTH"}`로 시작하고 `/settings`로 돌아온다. 재인증에서는 온보딩 캐시를 초기화하지 않으며 `profilePrefill`도 발급하지 않는다.

## 개인정보 화면의 다음 버튼

기본 정보·보호자 연락처 화면의 입력은 프론트 임시 상태에 보관한다. U01은 동의 없는 회원에게 빈 필드와 현재 version을 반환하므로 최초 PATCH 준비에도 사용할 수 있다. 기존 데이터는 해당 리소스 조회 결과로 초기화한다. 동의 전 U07 조회는 차단되므로 동의가 이미 유효한 회원만 기존 연락처를 조회한다.

다음 클릭 한 번에서 다음 순서로 실행한다. 전체 성공 후에만 다음 화면으로 이동한다.

1. U05 `POST /api/v1/me/consents`: 동의 3종을 version 1로 저장한다. 개인정보·AI 통화 필수 동의가 선택되지 않으면 프론트에서 진행하지 않는다. 위치는 선택이다.
2. U02 `PATCH /api/v1/me/profile`: U01의 version을 expectedVersion으로 보내 이름·번호 및 선택한 성별·생일을 확인·저장한다. 새로운 계정의 version은 1이다.
3. 보호자별로 U08 등록, U09 수정, U10 삭제를 호출한다. 보호자가 여러 명이면 실제 요청 수는 3개보다 많을 수 있다.

동의가 커밋돼야 개인정보 저장이 가능하므로 세 종류 요청을 Promise.all로 동시에 시작하지 않는다. 본인 번호와 보호자 번호의 충돌도 서버가 검사한다. 기존 보호자 번호를 본인 번호로 바꾸려면 충돌 보호자부터 수정/삭제한다.

독립 API는 일괄 트랜잭션이 아니다. 부분 실패 시 성공 결과·리소스 ID·version을 캐시에 반영하고 실패한 요청만 재시도한다. 같은 본문 재시도에는 같은 Idempotency-Key, 입력 변경에는 새 키를 사용한다. 409 VERSION_CONFLICT는 해당 리소스를 재조회하여 해결한다. 재로그인 후 기존 연락처를 다시 POST하지 않도록 U07의 ID를 활용한다.

U05에서 이미 GRANTED인 동의를 DECLINED로 변경하면 409 WITHDRAWAL_REQUIRED다. 실제 철회는 U06에서 수행한다. 문서 본문은 [정적 콘텐츠 계약](frontend-static-content.md)을 따른다.

## 이후 화면

- 마이크·위치 권한 요청 및 SOS 안내 확인은 프론트에서 처리한다. 다음/건너뛰기에 서버 요청이 필요하지 않다.
- 테스트 문자 작성 시 M01 `mode=TEST`, 일반 안심 문자 작성 시 `mode=SAFETY`를 호출한다. 둘 다 실제 프로필·개인정보 동의·연락처 조건을 검사한다.
- C01 통화는 회원 필수 동의와 확인된 이름·번호, 마이크 결과를 검증한다. 게스트는 기존 게스트 기능 범위를 사용한다.
- H01은 실제 데이터로 기능 가능 여부를 반환한다. ONBOARDING_REQUIRED는 없으며 PROFILE_REQUIRED, CONSENT_REQUIRED 등 원인을 사용한다.
- 프로필·보호자 연락처·동의·설정 변경은 해당 리소스 API를 사용한다. 프로필/연락처의 version은 잠금 버전이며 고정된 문서 version 1과 별개다.

## 기존 DB 적용

새 서버는 시작 시 JPA Entity를 기준으로 누락된 테이블과 컬럼을 자동 반영한다. 적용 전 DB를 백업하고 구형 서버와 worker를 중지한 뒤 새 서버와 프론트엔드를 함께 배포한다. 진행 중 OAuth는 만료될 수 있으므로 로그인을 다시 시작한다.

`ddl-auto=update`는 기존 컬럼과 테이블을 자동 삭제하지 않는다. 제거가 필요한 구형 온보딩 구조는 운영 데이터 보존 범위를 확인한 뒤 별도로 정리한다.

기존 AI 개인화 정책은 유지한다. 새 U02 입력의 성별·생일은 USER_CONFIRMED 출처이며, 과거 KAKAO 출처 데이터와 구분한다. 사용자가 입력한 값을 카카오 검증값으로 승격하지 않는다.
