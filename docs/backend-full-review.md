# 백엔드 전체 재검토 — 2026-09-14

아래는 수정 전 발견 기록이다. 두 문제의 수정 내용과 최신 결과는 [전체 재검토 수정 보고서](backend-full-review-fixes.md)를 참고한다.

검토 대상은 기존 보완 사항이 반영된 현재 작업 트리다. 이번 작업은 분석 요청에 따른 재검토이며, 아래 두 발견 사항에 대한 운영 코드 수정은 하지 않았다.

## 검토 범위

인증·OAuth·세션·쿠키, 사용자 정보·동의 철회, 계정 및 이용 기록 삭제, 통화 생성·발급·갱신·만료, 프롬프트 구성·게시, 암호화 키 생성·폐기, 메시지·홈·텔레메트리, 입력 검증·예외 처리·환경 설정 및 관련 DB 스키마와 테스트를 검토했다. 실제 Gemini Live 연결과 운영 외부 키 저장소를 사용하는 종단 간 검증은 포함하지 않았다.

## 추가 수정 필요 사항

### 1. [P2] 토큰 발급 대기 시간이 발급 처리 제한 시간에 포함됨

- 위치: `CallService.expire()` 및 `CallRepository.claim()` / `expired()`.
- `connectionGrant.createdAt`은 PENDING 생성 시각이다. ISSUING 전환 시각은 별도로 저장하지 않고, `claim(grant, now)`도 전달받은 `now`를 사용하지 않는다. 만료 처리는 생성 시각에 기본 10초를 더해 발급 제한 시간을 계산한다.
- 재현: 게스트 통화를 생성하고 테스트 시계를 11초 진행한 다음 워커를 실행했다. 세션 lease는 아직 유효하고 Gemini 모의 응답도 즉시 성공했지만, 외부 발급 호출 1회 후 통화가 `FAILED / CONNECTION_FAILED`, 발급이 `UNKNOWN`으로 바뀌었으며 토큰은 저장되지 않았다.
- 영향: 워커 지연이나 대기열 적체가 발생하면 실제 발급이 빠르게 성공해도 사용자는 통화를 시작하지 못한다. 이미 제한 시간을 넘긴 요청이 외부 발급까지 실행되는 문제도 있다.
- 권장 수정: 발급 시작 시각을 저장하고 ISSUING 제한 시간을 그 시각부터 계산한다. 생성부터의 전체 대기 제한이 필요하다면 별도 정책으로 두고 외부 호출 전에 검사한다. 일반 만료 처리와 만료 대상 조회 조건을 함께 변경해야 한다.

### 2. [P2] 키 생성 복구 기록이 동일 DB 연결 풀에서 중첩 연결을 요구함

- 위치: `KeyDiscardQueue.prepareCreation()` 및 `TransientKeys.create()`.
- 외부 업무 트랜잭션이 연결을 보유한 상태에서 같은 트랜잭션 관리자의 `REQUIRES_NEW`로 복구 기록을 커밋한다. 동시 요청이 풀의 모든 연결을 차지하면 각 요청이 추가 연결을 기다리다 실패할 수 있다.
- 재현: 별도의 Hikari 풀을 최대 4개 연결, 연결 대기 제한 700ms로 구성했다. 4개 업무 트랜잭션이 모두 연결을 획득하도록 동기화한 뒤 동시에 현재 `TransientKeys.create()`를 호출했다. 최소 1개 요청이 `CannotCreateTransactionException`으로 실패함을 확인했다. 이는 구성 요소 동시성 재현이며, 운영 HTTP 부하 테스트 결과는 아니다.
- 영향: 키를 생성하는 로그인·토큰 저장 등의 경로가 요청 집중 시 DB 연결 대기 오류로 실패할 수 있다. 현재 설정의 연결 대기 제한은 3초다.
- 권장 수정: 복구 기록용 연결 자원 분리 또는 외부 업무 트랜잭션 진입 전 복구 기록 준비 구조를 검토하고, 동시 실행 상한을 연결 용량과 함께 설계한다. 단순 풀 크기 증가는 포화 조건을 늦출 뿐이다. `REQUIRES_NEW`를 `REQUIRED`로 바꾸면 롤백 후 복구 기록 보존을 잃으므로 그렇게 해결해서는 안 된다.
- 근거: Spring 공식 문서도 외부 트랜잭션이 연결을 보유한 채 내부 트랜잭션이 새 연결을 요구하면 풀 고갈 및 대기 문제가 생길 수 있음을 설명한다: [Understanding PROPAGATION_REQUIRES_NEW](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html).

## 검증 결과와 한계

- `scripts/verify_auth.py`로 서비스 DB와 분리된 임시 MySQL에서 실행했다.
- 기존 단위 테스트 51개와 통합 테스트 143개가 모두 통과했다.
- 위 문제의 현재 동작을 단언하는 임시 재현 테스트 2개도 통과했다. 합계 196개, 실패·오류·건너뜀 0개다. 재현 테스트의 통과는 결함이 수정되었다는 뜻이 아니다.
- 재현용 테스트를 삽입했던 `WebIntegrationTest.java`는 검토 시작 전 파일로 복원하고 SHA-256 일치를 확인했다. 기존 사용자 작업과 이전 수정 사항은 유지했다.
- 재현 코드와 결과 XML은 각각 `build/full-review/probes.java.txt`, `build/full-review/results.xml`에 보관했다. 이 경로는 빌드 산출물이며 버전 관리 대상이 아니다.
- 이번 검토에서는 Swagger 경로·메서드·요청 및 응답 형식이나 운영 코드를 변경하지 않았다.
- 그 외 검토 범위에서는 추가로 재현하거나 확정할 수 있는 결함을 찾지 못했다. 실제 외부 서비스와 운영 부하 조건까지 문제가 없음을 보증하는 결과는 아니다.
